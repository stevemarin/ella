# JIT and runtime-code background

## 1. Purpose and scope

This note preserves the background behind the current Ella runtime-code
discussion:

* what Ella's current compiler and staging implementation do;
* what the consulted documentation says about compiling Python with mypyc
  and Cython and embedding CPython;
* what the copy-and-patch paper and its project references say about
  stencils and composition;

The external pages were retrieved for research on 2026-11-04. Their relevant

## 2. Current Ella facts

The following observations are based on the checked-in source and docs:

1. Ella's front end, checker, IR and interpreter are implemented in Python;
   native executables use x64 assembly generated by the Python compiler and a
   C runtime.
2. `run(code)` in the IR interpreter checks the generated expression, lowers
   it into a function in the current module, verifies the module, then invokes
   that function in the IR interpreter.
3. The native backend currently errors if runtime execution reaches
   `quote`, `run`, runtime type values, or reflection operations. Staging is
   available while compiling, but native code has no runtime compiler.
4. The Python IR interpreter and native code do not currently share a value
   representation. Python interpreter values are Python objects; the C
   runtime represents values as 64-bit words, with pointers to runtime
   objects for boxed values. The IR interpreter also simulates/checks arena
   placement with Python-side tags, while native code uses the C runtime's
   arenas.
5. Therefore, reusing native C helpers from the current Python interpreter
   requires a representation and lifetime bridge. A native IR VM using the C
   runtime representation could avoid that particular mismatch, but would be
   another implementation of the IR execution semantics.
6. An embedded VM would not alone solve arbitrary runtime `run`: generated
   syntax still needs checking and lowering into a representation the VM can
   execute.

## 3. Python implementation compilers and embedding

### 3.1 mypyc

The mypyc documentation describes mypyc as compiling Python modules to C
extensions using type hints. Its stated execution model remains CPython:
compiled modules are imported and run by Python, and can interact with
ordinary Python modules.

The documentation also describes a gradual Python subset and behavior
differences that enable performance, including runtime type checks for some
annotated or inferred values, early binding within compilation units, and
unboxed representations for some values. These details matter if considering
compiling Ella's interpreter: it should not be assumed that compiling its
Python implementation makes it a standalone VM or that every Python behavior
is unchanged.

**Implication for Ella:** mypyc may be worth testing to speed up or distribute
the Python-hosted compiler/interpreter. It does not translate Ella IR to
machine code and, by itself, does not remove CPython from the deployed
program. It is not a direct route to a compact Python-free Ella executable.

References:

* [mypyc: Introduction](https://mypyc.readthedocs.io/en/stable/introduction.html)
  — compilation to C extensions, CPython execution, supported use cases.
* [mypyc: Compilation units](https://mypyc.readthedocs.io/en/stable/compilation_units.html)
  — early binding within a unit and late-bound interactions across units.
* [mypyc: Differences from Python](https://mypyc.readthedocs.io/en/stable/differences_from_python.html)
  — documented runtime checking, primitive representation and binding
  differences.

### 3.2 Cython

Cython's source compilation guide describes translating `.py` or `.pyx` to C
or C++, then building extension modules. Its embedding guide documents
generating a C `main` and registering compiled modules, while initializing
CPython and importing those modules before use.

Cython can therefore be used in a host executable, but that is not the same
as compiling Ella IR to native instructions, and it does not remove the Python
runtime. Cython's early-binding guide also explains that C-level declarations
can avoid dynamic Python lookup and call overhead, at the cost of using more
static declarations and C-level interfaces.

**Implication for Ella:** Cython could be an experiment for the speed or
packaging of the Python compiler/interpreter. It does not eliminate the need
to decide how runtime Ella code is checked/lowered or how it executes. As
with mypyc, a Cython-compiled interpreter would still interpret Ella IR.

References:

* [Cython: Source Files and Compilation](https://cython.readthedocs.io/en/latest/src/userguide/source_files_and_compilation.html)
  — translation to C/C++ and extension-module builds.
* [Cython: Embedding Cython modules in C/C++ applications](https://cython.readthedocs.io/en/latest/src/tutorial/embedding.html)
  — generated main, module registration, CPython initialization and linking.
* [Cython: Early Binding for Speed](https://cython.readthedocs.io/en/latest/src/userguide/early_binding_for_speed.html)
  — typed declarations and C-level access/calls.

### 3.3 CPython embedding

Python's embedding documentation describes a native host initializing the
Python interpreter and calling Python code through the C API. Embedding
provides a way for a non-Python application to use Python code; it is not a
standalone compilation of that code without Python.

**Implication for Ella:** compiling the Python sources and embedding them
could make a native host call the existing compiler/interpreter, but the
executable would depend on CPython and the relevant Python modules. The actual
distribution size, startup overhead and memory usage depend on build and
packaging choices; no figures were verified for Ella, so no numerical cost is
claimed here.

Reference:

* [Python: Embedding Python in Another Application](https://docs.python.org/3/extending/embedding.html).

## 4. Copy-and-patch research

### 4.1 Primary paper

Haoran Xu and Fredrik Kjolstad,
[“Copy-and-Patch Compilation: A Fast Compilation Algorithm for High-Level
Languages and Bytecode”](https://doi.org/10.1145/3485513), *Proceedings of the
ACM on Programming Languages*, OOPSLA 2021. An open version is available as
[arXiv:2011.13127](https://arxiv.org/abs/2011.13127).

The paper's abstract and available paper record describe:

* **Stencils:** binary implementations with holes for values to insert during
  code generation.
* **Library construction:** stencil generators are used to construct a
  library of binary variants.
* **Runtime compilation:** the compiler selects, copies and patches stencil
  variants to produce code.
* **Composition:** fragments are combined to compile operations and control
  flow, with patching/fixups for values and targets.
* **Applications:** a compiler for a high-level C-like metaprogramming
  language and a WebAssembly compiler.

This is evidence that copy-and-patch can compile beyond a fixed menu of
whole-function templates. It is not evidence that arbitrary machine-code
stencils can be generated automatically from misses. The described library
construction starts from stencil generators supplied to the system; the
compiler composes available variants.

### 4.2 Associated implementations

The paper and project material identify:

* [PochiVM](https://github.com/sillycross/PochiVM), a C++ framework for code
  generation whose repository describes a copy-and-patch baseline compiler;
* [WasmNow](https://github.com/sillycross/WasmNow), the WebAssembly
  implementation associated with the paper.

These projects are useful implementation references, but their languages,
IRs, ABIs, and runtime needs differ from Ella's. They do not establish that
Ella can directly reuse their stencils.

### 4.3 Iterative stencil-library growth versus automatic synthesis

The phrase “iteratively generate stencils” can mean two distinct processes:

1. **Human-guided coverage growth:** execute or compile a corpus, report
   unsupported shapes, write a generator for a missing stencil family, and
   repeat. This appears practical and matches a learning-project workflow.
2. **Automatic synthesis or learning:** derive a valid machine-code stencil
   from a compilation miss or execution trace without a programmer writing
   the generator. The primary paper above does not describe this as its
   library-building method.

The bounded search for this note did not locate a primary paper specifically
about an automatically learned, open-ended copy-and-patch stencil library.
This is a limit of the search, not proof that no related work exists. It may
be more productive to search adjacent literature under terms such as
instruction selection, superoptimization, trace compilation, staged
metaprogramming, and binary rewriting.

### 4.4 Compositional abstraction

The paper's model already provides an abstraction above copying raw bytes:
select a stencil corresponding to a logical operation, then compose and patch
stencils into a function. Ella could put its own explicit layers above that:

1. machine snippets with declared clobbers, stack effects and relocations;
2. typed-IR operation templates that select snippets by operation and type;
3. block/function assembly that allocates locations and resolves branches,
   calls and relocations.

This layered design is a proposed adaptation, not a claim that the paper
provides Ella's register allocation or ABI. The contract between fragments is
the difficult part: register and flag effects, stack alignment, calling
conventions, branch ranges, error paths and runtime helper calls must compose
correctly. A stencil selector does not remove these backend obligations.

### 4.5 Related but adjacent work

The research agent identified the 2026 paper
[“Leveraging Copy-and-Patch JIT for Low-Overhead Dynamic Program
Analysis”](https://doi.org/10.1145/3828170.3828176), by Matěj Kocourek,
Filip Křikava, Pierre Donat-Bouillud, and Jan Vitek, as adjacent work on using
copy-and-patch JIT for dynamic analysis. The ACM page could not be retrieved
in this review (HTTP 403), so this reference is retained as a literature lead,
not used to support detailed claims. It is not, based on the available
description, a paper about automatically synthesizing a stencil library.

## 5. Design analysis for Ella

This section is reasoning based on Ella's current implementation and the
sources above. It should not be confused with claims made by those sources.

### 5.1 Runtime execution has a front-end requirement

Dynamic `run(code)` begins with a `Code[T]` value, not with a machine-code
function. The current IR interpreter checks the generated syntax and lowers
it to IR before executing it. Therefore:

* A native IR VM needs a compiler path from generated code to executable IR.
* A copy-and-patch backend needs the same path, plus native code generation for
  the produced IR.
* AOT quote templates can bypass runtime compilation only when the quote's
  final shape is known early enough.

This front-end/back-end distinction is a useful guard against conflating
“embedding the interpreter” with “supporting native runtime staging.”

### 5.2 The C runtime: share the substrate, not necessarily the interpreter

The current Python interpreter and C runtime have different object models and
memory accounting. A bridge for selected operations from Python to C is
possible, but may be awkward and expensive relative to the work performed.
It can still be useful for differential tests or for a few operations where
sharing the exact native implementation is valuable.

If Ella wants an embedded native VM, a more consistent design is for that VM
to use the same value representation, arenas and runtime ABI as generated
native code. That could allow interpreted and compiled functions to exchange
values. It also means the VM must implement runtime semantics against the
native representation. Keep the existing Python interpreter as a semantic
reference rather than requiring it to use C layouts.

The appropriate split between VM instructions and C helpers is an empirical
question. A VM might implement simple scalar operations and branches itself,
while calling the C runtime for complex operations, allocation, text/equality,
errors, or host interactions. Fine-grained helper calls may add overhead;
coarse helpers may complicate control flow and traces.

### 5.3 Interpreter instrumentation can guide, not prove, stencil coverage

The IR interpreter sees functions lowered both during initial compilation and
at runtime `run`. It can gather at least two useful datasets:

* **Static shape coverage:** every instruction, block, terminator, type and
  call form in each complete lowered function.
* **Dynamic use frequency:** which instructions/functions execute and how
  often in a workload.

These must remain separate. A branch not taken still has to be emitted for a
compiled function; frequency helps prioritize hot operations but cannot show
which instructions a complete function needs.

For runtime staging, an especially useful hook is after `check_code` and
lowering produce a function, but before that function executes. At that point,
the tool can record the whole generated shape. A future prototype could:

1. normalize and fingerprint the lowered function;
2. ask a stencil backend whether it supports that shape;
3. execute with the IR VM/interpreter on a miss;
4. save the miss as a regression case;
5. count execution frequency separately; and
6. use the accumulated corpus to decide which stencil families to implement.

This is data-driven prioritization. It is not completeness: unseen programs,
unexecuted branches, new type combinations and target-specific codegen
constraints remain. Coverage criteria should eventually enumerate the
supported combinations rather than rely only on observed workloads.

Instrumentation should avoid logging actual user constants, source contents,
or captured values unless explicitly needed. For stencil coverage, constants
can normally be recorded by category (immediate versus runtime argument,
address, or relocation) rather than by their value.

### 5.4 Shape restrictions are the key to template viability

Stencils and AOT quote templates become simpler if runtime values supply data
but do not determine the code structure. Candidate restrictions include:

* statically known quote structure and control flow;
* statically known shapes for spliced code;
* statically resolved types, method targets and layouts; and
* captures passed as runtime arguments rather than baked into code.

These restrictions can make generated code a template-selection problem.
They exclude or complicate cases where runtime loops or values decide the
number of generated expressions or blocks. Ella's compile-time staged
programs that generate code from known types are natural template candidates;
arbitrary runtime-dependent code composition is not.

The language-level choice is whether those dynamic cases should be
interpreted, rejected in native executables, or supported by a general
runtime compiler. An embedded VM fallback permits broad support without
requiring every shape to have a stencil.

### 5.5 Self-hosting changes the implementation and deployment costs

If Ella's compiler and VM are self-hosted and can be linked into native Ella
programs, the runtime compiler need not invoke Python. This makes an
Ella-written VM or stencil assembler plausible and provides a route to
runtime checking/lowering.

Self-hosting alone does not provide:

* a VM ABI for host programs;
* a native object model or bridge between compiled and interpreted code;
* executable-memory management;
* instruction encoding, relocations or runtime code patching; or
* a JIT backend.

Self-hosting would make the hybrid design more attainable, not remove the
design choice. A self-hosted IR VM could be the correctness path and
copy-and-patch could accelerate the covered subset.

## 6. Proposed evidence-gathering experiment

Before deciding on a general JIT, gather data from a small, explicit
prototype:

1. **Specify the scope.** List which runtime quote/splice/reflection cases
   must work in native executables, and which may remain unsupported.
2. **Instrument compilation products.** Record normalized IR for every
   function, including functions produced by runtime `run`, and count actual
   execution separately.
3. **Run a corpus.** Include existing test programs, examples, generated-code
   tests, and hand-written staging cases varying types, branches, calls,
   loops, methods, arrays, and captures.
4. **Report coverage and misses.** Group by operation/type/control-flow
   shape. Preserve unsupported generated functions as reproducible test
   cases.
5. **Implement a narrow backend.** Add a small stencil subset and use the VM
   or interpreter as fallback. Compare results and failures with the
   reference interpreter.
6. **Measure decisions, not only speed.** Record compilation latency,
   execution latency, executable/runtime footprint, VM fallback rate,
   stencil coverage and maintenance burden.
7. **Revisit runtime representation.** If the experiment justifies a native
   VM, measure whether it should share the C runtime ABI and where C helper
   boundaries belong.

The experiment distinguishes three claims:

* **Observed:** this corpus produced these IR shapes.
* **Covered:** this backend can compile these enumerated shapes.
* **Complete for a language subset:** every program allowed by a documented
  restriction compiles or has a defined fallback.

Only the last claim is a language guarantee. Profiling supplies evidence for
priorities; it cannot substitute for a definition of the supported subset.

## 7. Research limitations and confidence

* The mypyc, Cython and CPython statements above are based on official
  documentation. They establish the runtime model and documented build
  workflow, but do not quantify Ella-specific package size or performance.
* Copy-and-patch claims are based on the primary paper record/abstract and
  project pages. The ACM full-text page was inaccessible during retrieval;
  use the arXiv paper for a full technical review before adopting details of
  its algorithms.
* The lack of a directly relevant automatic stencil-synthesis paper is a
  bounded search result, not a definitive literature survey.
* The adjacent 2026 dynamic-analysis paper is included as a lead; its ACM
  page returned HTTP 403, so no technical details are asserted.
* Proposed VM, ABI, instrumentation and hybrid architecture choices are
  design hypotheses for Ella. They need prototype data and differential
  tests.
